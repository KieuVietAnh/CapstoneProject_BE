# EF Core and migrations

Read this reference for entity, schema, constraint, index, query-shape, or migration work.

## Baseline

- Projects target .NET 9.
- Audited packages are EF Core 8.x and Npgsql EF provider 8.x; confirm exact current versions in `.csproj` files.
- EF mappings and relationship rules live in `UrbanService.DAL/Data/UrbanServiceDbContext.cs`.
- Entities live under `UrbanService.DAL/Entities/`.
- Migrations and `UrbanServiceDbContextModelSnapshot.cs` live under `UrbanService.DAL/Migrations/`.

## Schema-change workflow

1. Confirm the user asked for a schema change; do not infer one from a documentation or diagnosis request.
2. Inspect the entity, mapping, repository/query, newest related migration, and model snapshot.
3. State the invariant and choose the database mechanism that enforces it: foreign key, check constraint, unique/filtered index, required/nullability rule, precision, or transaction.
4. Create a new migration for an intended model change. Do not edit an already-published migration merely to make the current model look consistent.
5. Inspect generated `Up`, `Down`, designer, and snapshot changes. Remove unrelated model churn only when it is clearly generated by the current operation and safe to do so.
6. For data movement or new non-null constraints, define a safe backfill/order of operations and rollback behavior.
7. Run focused tests, the test project, solution build, migration/model checks available in the repo, and diff checks.

Do not run `database update`, SQL against a shared database, or any destructive database operation without a clearly identified authorized target. Generating a migration does not authorize applying it.

## High-risk checks

- Filtered unique indexes must use SQL compatible with PostgreSQL and the stored string casing.
- Link status and timestamp fields should be protected by a check constraint, not only service order.
- Uniqueness errors and concurrency races need a stable API/service outcome.
- Deletion behavior must preserve required audit/history and avoid orphaning rows.
- Query changes should remain server-translatable and cancellation-aware where the current contract supports it.
- Never print or commit real connection strings, provider tokens, or secrets while diagnosing EF tooling.
